# Compatibility with Codex app-server 0.160.0

This document describes implemented behavior, not full protocol equivalence or a guarantee about future Codex/Claude releases. The wire schema is `protocol/codex-0.160.0.json`.

## Client methods

Accepted requests are validated against the pinned schema before execution, with supplemental schemas for legacy `getAuthStatus` and `thread/rollback` RPCs omitted from the export. Fields below are the supported non-null fields; unsupported non-null fields fail. Values must also satisfy the upstream schema.

| Method | Supported fields / behavior |
| --- | --- |
| `initialize` | `clientInfo`, `capabilities.experimentalApi`, `capabilities.optOutNotificationMethods`; requests accepted immediately after reply; optional `initialized` |
| `thread/start` | `cwd`, `model`, `modelProvider`, `approvalPolicy`, `sandbox`, `baseInstructions`, `developerInstructions`, `ephemeral`, `historyMode`, `projectId`, `threadSource` |
| `thread/resume` | `threadId` or returned `path`, `cwd`, `model`, `modelProvider`, `approvalPolicy`, `sandbox`, `baseInstructions`, `developerInstructions`, `excludeTurns`, `initialTurnsPage`; snapshot cursors and unchanged active settings supported |

| `thread/inject_items` | Idle thread; user messages containing `input_text` only; queued model-visible context before the next user input, without starting a turn |
| `thread/revert`, `thread/rollback` | Idle loaded thread; retain the prefix before `beforeTurnId` (paginated) or remove `numTurns` (legacy); next native turn forks at the retained UUID |

| `app/list`, `app/installed`, `app/read` | Not served by the facade. Behind the desktop router, a request naming a Claude thread goes to genuine Codex without its `threadId`, which only selects Codex's per-thread app configuration |
| `configRequirements/read` | Full-access/workspace-write, on-request/never approvals, user/native auto review |
| `collaborationMode/list` | Empty list: no Codex collaboration presets |
| `experimentalFeature/list` | `cursor`, `limit`; empty list: no Codex experimental features |

`historyMode` and `projectId` on `thread/start`, and `projectId` on `thread/list`, require `initialize.capabilities.experimentalApi: true`, matching their absence from the pinned stable schema.

Only provider `anthropic` is accepted. Model aliases and identifiers are sent to Claude; the backend decides availability. Supported effort values are `low`, `medium`, `high`, `xhigh`, and `max`; a particular model may reject an otherwise valid effort. No effort is forced by default.

Service tier `priority` (Codex's Fast tier) and its legacy name `fast` select Claude fast mode; `default` or null selects standard speed. `serviceTierForTurn` overrides one turn without changing the thread's tier. Claude Code accepts fast mode from SDK sessions only as a launch flag setting, so the facade passes `fastMode: true` through `--settings`, and changing the tier starts a new process. Claude decides whether fast mode can serve a request (model support, plan, extra usage, rate-limit cooldown) and otherwise runs at standard speed; when a turn asked for fast mode and Claude reports it did not use it, the turn emits a `warning` with Claude's reason. Other tiers are rejected, and ACP agents reject fast mode.

Desktop submission options are translated before dispatch: `approvalsReviewer: user` uses the native human approval callback; desktop guardian/auto-review selections use Claude native auto review, not a Codex reviewer. `experimentalRawEvents: false` is accepted. `disabledPluginIds` persists per thread and becomes a native `enabledPlugins` launch override. Additive `config.shell_environment_policy` overlays persist and become native `env` settings; restrictive inheritance/filtering/profile policies fail explicitly. Absolute `runtimeWorkspaceRoots` are workspace metadata, not filesystem confinement. Default collaboration mode maps its model and effort; plan mode remains unsupported. Turn trigger/client analytics and the deprecated `multiAgentMode` do not affect execution. Additional context is passed as reference text to Claude. Codex runtime feature overrides and app-tool allowlists produce warnings because Claude uses its own runtime/tools; they do not enable Codex-only features or connect app-provided tools. Dynamic function/namespace definitions are persisted with the thread and exposed through the Claude SDK MCP transport. Calls use item/tool/call on the turn owner, validate arguments, and map client success/error and text/image/audio results back to MCP; the desktop remains responsible for its own tool approval UI. The deprecated personality field is accepted as a no-op. Other unsupported options are reported together rather than one at a time.

The local desktop's `memories.dual_write`, `memories.version`, and desktop MCP overrides (`mcp_servers.node_repl`, `mcp_servers.artifact_session`, `mcp_servers.cua_repl`) are filtered with a warning and do not configure Claude. Both enabled runtime definitions and disabled placeholders are accepted. Claude retains its native memory and MCP settings; this does not add native CUA or viewer-bound artifact-session access. Other unsupported memory and MCP overrides are rejected. The router preserves genuine Codex requests and their runtime configuration.

`baseInstructions` maps to `--system-prompt`; `developerInstructions` maps to `--append-system-prompt`. An idle resumed thread can refresh both instruction fields, model, cwd, or approval policy. The facade disables native system-prompt snapshots so refreshed instructions take effect while native conversation history is preserved. Resuming during an active turn ignores these overrides.

After a turn finishes cleanly, the thread keeps its Claude process (and Codex plugin runtime) idle. The next turn reuses it when its launch is unchanged: same model, effort, service tier, permission mode, cwd, sandbox, instructions, dynamic tools, plugin and environment overrides, and no output schema, rewind, or fork. The sandbox is compared as enforced, not as spelled: writable roots are resolved, deduplicated and sorted, the working directory (always writable) is implied, and, as in Codex, `/tmp` and `$TMPDIR` are writable unless excluded. The desktop lists the temporary directories only on a chat's first turn, which would otherwise relaunch Claude on its second. A fresh launch renders Claude's request prefix again, and any difference (MCP servers that connect in a different order, a rebuilt plugin catalog) invalidates the prompt cache for the whole conversation. Otherwise the idle process closes and the turn resumes the session in a new one. Idle processes also close after `--idle-session-timeout-seconds` (default one hour, Claude's longest cache lifetime), when more than `--max-idle-sessions` are idle, and on archive. Closing happens in the background, so it never holds up other threads; a thread's next process starts only after its previous one has exited. Claude can start work while no turn is open: a background command, monitor, or agent outlives its turn, and Claude answers its notification on its own. Codex has no equivalent, so the facade opens a new turn on the thread (no user message) and streams that work into it. The turn's approvals go to a client subscribed to the thread, or wait for one to resume it. A process with background work still running is not an idle cache: it does not expire or count toward `--max-idle-sessions` until the work finishes (then Claude gets at least a minute to answer), and it is kept even when reuse is disabled or the turn's launch was turn-specific, though it then never serves a later turn. Two cases still stop the work, and the thread gets a `warning` saying how many tasks were stopped: archiving the chat, and a turn that needs a new Claude process (changed launch settings, rewind, or fork). A turn requested while Claude is opening its own turn is rejected until that turn starts. Plugin installations made while a process is idle reach the thread on its next new launch. A new process waits up to 30 seconds for MCP servers that are still connecting before its first prompt: Claude Code otherwise sends that request without them, and their tools joining the next request invalidate the cache again.

## Notifications and tool translation

Implemented notifications include `thread/started`, name/archive/unarchive/status changes, `thread/deleted`, `thread/tokenUsage/updated`, `turn/started`, `turn/completed`, `turn/plan/updated`, `item/started`, `item/completed`, assistant/reasoning/command deltas, `serverRequest/resolved`, `thread/reverted`, attachment updates, and `error`.

| Claude content | Codex representation |
| --- | --- |
| Text blocks and streaming text | `agentMessage`; partial/final messages reconciled without duplicate text |
| Exposed thinking blocks | `reasoning` and text deltas |
| `Bash` | `commandExecution`, result output, exit code only when supplied by Claude |
| `Write`, `Edit`, `MultiEdit` | `fileChange` with best-effort proposed diffs from small UTF-8 files |
| `mcp__server__tool` | `mcpToolCall` |
| Other native tools | `dynamicToolCall` in namespace `claude` |
| `TodoWrite` | Tool item plus `turn/plan/updated` |
| `Agent` (subagent) | `collabAgentToolCall` `spawnAgent` and `wait` items plus a linked child thread; see below |
| Compaction (manual or automatic) | `contextCompaction`, started at Claude's `compacting` status and completed at its compaction boundary. Like Codex v2, no deprecated `thread/compacted` notification |
| Structured output | Final assistant message containing JSON |

### Subagents

Claude subagents map to Codex child threads, following Codex's multi-agent (v1) wire shape. The facade asks Claude to forward subagent text (`forwardSubagentText`).

- An `Agent` call starts a `spawnAgent` collab item on the calling thread. When Claude reports the task (`task_started`), the facade creates a persisted child thread and completes the spawn item with it as receiver. A `wait` item stays open until the agent finishes: the Agent tool result for a foreground agent, or the task notification for a background one. The `wait` item's agent state carries the final report.
- The child thread has `parentThreadId`, `source.subAgent.thread_spawn` (parent, depth, nickname from the agent `name` or description, role from `subagent_type`), and `threadSource: subagent`. Like Codex, it emits no `thread/started`. Every initialized connection is subscribed when a child turn starts, and receives `turn/started`, item lifecycles, usage, and `turn/completed` on the child thread. Claude sends subagents' messages and tool calls whole, without streaming deltas.
- Subagent permission requests and questions are shown on the child thread and turn, and mark both the child and the root as waiting. The native callback still belongs to the root turn.
- A nested agent emits no transcript frames of its own. Its child thread, linked under the calling subagent's thread, shows the prompt and the final report.
- A message to an existing agent (`SendMessage`) continues it in a new turn on the same child thread, including after a facade restart. The `SendMessage` call itself remains a `dynamicToolCall`.
- Child threads are read-only: `turn/start`, `thread/fork`, and history recovery reject them, and `canAcceptDirectInput` is false, because Claude cannot resume a subagent transcript as its own session. Interrupting or failing the root turn ends open child turns. Child token usage reports the subagent's latest request and, for foreground agents, the total from the Agent result. The root thread's totals remain Claude's parent-only usage.
- Workflow agents and agents whose task cannot be linked keep the earlier representation: a `Background agent`/`Background workflow` item on the root turn.

File diffs are previews, not an OS audit; command-mediated file edits do not synthesize file-change items. Tool output arrives when Claude emits its tool result, so command output is not necessarily streamed while the process runs. Structured/multimodal tool results are currently rendered as text, including serialized non-text blocks; native MCP result metadata is not preserved.

`summary: none` suppresses reasoning items; `auto` exposes native text. `concise` and `detailed` expose native text with a warning because the facade cannot impose those summary lengths. The facade forwards only reasoning text Claude actually exposes. Claude's local-agent/local-workflow tasks and session state are tracked to keep stdin open for continuations and permission requests after an intermediate result. Claude versions without session-state events fall back to the result plus observed task state.

## Permissions and lifecycle

- `on-request` uses Claude `manual`. `never` with `danger-full-access` (the desktop's Full access) uses Claude `bypassPermissions`; `never` inside the workspace sandbox uses `dontAsk`, which denies whatever would prompt. Under `never`, callback permission requests are denied rather than shown; native user questions remain answerable.
- Commands use `item/commandExecution/requestApproval`; file writes use `item/fileChange/requestApproval`. Supported decisions are `accept`, `acceptForSession`, `decline`, `cancel`. Session grants match the exact tool name, complete input and cwd within this thread, persist across facade restarts, and are not copied to forks. Native broad rule amendments remain rejected.
- Desktop tool execution has no approval deadline; the client response, cancellation, or native turn termination ends it. Transport loss does not cancel it.
- Single-select `AskUserQuestion` calls use `item/tool/requestUserInput`. Calls containing multi-select questions use sequential `item/tool/requestOptionPicker` requests with fresh IDs, the installed desktop extension documented in [approval design](docs/approval-design.md). Skip/dismiss denies the native call without partial answers. Generic tool permissions offer once/session/deny. Only the live owner, or its replacement after disconnect, can answer pending requests.
- Each facade thread has at most one active turn. Separate threads have independent Claude processes. Resuming an active thread subscribes the client and returns its current state; as in Codex, setting overrides in that request are ignored (and logged) rather than rejected, since the running turn keeps its launch settings.
- Disconnecting the turn owner detaches it without stopping Claude. Resume claims a detached turn, returns current streamed state, then replays pending requests with their original IDs/call IDs. A delayed result with the original request ID can claim after initialization, before resume. Approval deadlines count connected time only. A live owner cannot be displaced by an observer. Slow clients are disconnected when their bounded output queue fills. Host command/PTY processes remain connection-owned and terminate on disconnect.
- Interrupted runs drain transcript events through a result/exit for up to five seconds before forced termination. All forced cancellations await process cleanup before publishing the terminal frontend state. Native descendants in the backend process group are terminated on Unix.
- One native process runs per facade turn. Claude-native background shells are not guaranteed to survive the turn; a completed task is not a persistent terminal service.
- Facade records are written atomically with private file permissions and a process-exclusive directory lock, by one background writer that keeps writes in order. Streamed progress is saved within a quarter second of arriving (a burst becomes one write) and the native session identity immediately; request handlers and turn completion wait for their writes. A crash can lose up to that last quarter second of streamed items. Recovering an active saved turn after a facade crash marks it interrupted. Persistence does not coordinate arbitrary outside clients using the same native Claude session.
- `threadId` identifies the facade record. The returned `sessionId` groups a source thread and its forks as in this pinned protocol. Native Claude session IDs are private metadata and are not interchangeable with either field.
- Fork/revert/rollback use `--fork-session --resume-session-at` at an exact per-turn native UUID. Empty history starts fresh. Missing anchors fail closed; old records support full snapshot forks only when their latest anchor is known. Forking a running Claude parent snapshots its completed turns and leaves its active turn running; explicit boundaries cannot retain an in-progress turn. Recovery does not undo files, external effects or native persistent memory.
- Disconnect recovery lasts while the facade process runs. Facade shutdown/restart interrupts active native work. Stable call IDs allow the desktop to deduplicate reconnect replay; exactly-once effects across a full desktop process crash are not guaranteed.
- Pagination cursors bind to list scope, filters, direction, and an item anchor. If the anchor is removed from that list, the cursor errors. Limits are 1–1000. Summary requests can receive full items labeled `full`.

## Explicit limitations

- Workspace-write enforces Claude’s native Bash sandbox and scoped file permissions. Native auto review accepts installed desktop guardian payloads. MCP and hooks are trusted integrations outside the Bash sandbox; read-only and external profiles are unsupported. Resolved restrictions are checked before model input.
- No raw transcript import, realtime audio, remote control, login, quotas, remote environments, collaboration modes, or other unlisted RPCs. Codex skills/hooks management and MCP services are forwarded when configured; Codex hook execution around Claude turns and interactive MCP elicitation are unsupported.
- Inputs: text, supported image data/HTTP(S) URLs, and local PNG/JPEG/GIF/WebP paths. Behind the desktop router, local paths in turn, steer and queue input are read by the router and sent to the facade as data URLs, because files such as screenshots dragged from the capture thumbnail can be opened only by the desktop's process tree. No OpenAI file IDs, image detail selection, audio, video, skill, or mention input mapping.
- Ephemeral threads use `--no-session-persistence` and remain out of disk/list history. A durable parent can fork into an ephemeral side chat with instruction overrides and an injected boundary. Follow-ups retain its Claude process until the chat is archived or its last subscriber unsubscribes; idle cache limits and expiry do not discard temporary history. Launch-setting changes and a lost process fail explicitly instead of restarting without history. Ephemeral threads cannot be a fork source or recover their history.
- Model listing is the installed Claude CLI's catalog, not an inference entitlement check. Config reads declare the Claude custom provider; model/effort default writes and Codex plugin enable edits are supported. Plugin configuration and authentication remain owned by genuine Codex.
- Native authentication and API failures produce failed turns; there is no credential management or provider failover.
- Validated on macOS. Windows process-tree cleanup and Unix-only transports are not interchangeable; Windows support is not claimed.
- Live inference, restart recall, fork isolation, and a real tool approval passed earlier on October 8, 2026. The expanded installed-service probe also passed first turn/tool roundtrip, saved-path resume, timeline, host command, and queued context-preserving followup. Two-input steering passed separately against live Opus. The current build passed 91 deterministic tests and installed SSH reconnect with one recovered tool result; earlier fork/revert excluded removed native context, and the environment overlay reached a real Bash tool. Native desktop rendering remains unverified because computer-use access is denied. See [the workflow audit](docs/desktop-integration-audit.md) for the complete known gap map.

The installed desktop host API also supports `process/spawn`, `process/writeStdin`, `process/kill`, and `process/resizePty`, with immediate spawn acknowledgement, binary output notifications and exit notifications. Explicit null caps/timeouts follow that API’s unlimited semantics. New threads default to workspace-write. Native Read approvals use filesystem permission requests; generic tools retain explicit question-based approval.

Context usage now reports the latest top-level Claude model request, including cache tokens; cumulative turn billing remains separate. Updates stream during turns and replay on resume. Legacy inflated context readings remain unknown until fresh native usage arrives. The denominator uses the actual main model rather than a larger auxiliary model.

Native auto review can deny an action before Claude emits `can_use_tool`; no
human callback exists for the facade to approve in that case. The denial is
preserved and surfaced. To request manual review, select **Ask for approval** for
that chat and ask Claude to retry the specific action. The facade does not switch
modes automatically or install global permission allow rules. Explicit configured
deny rules still apply. This boundary was checked against Claude Code 2.1.294.

## ACP agents

With `--acp-agent`, the same Codex surface is served by an [Agent Client Protocol](https://agentclientprotocol.com) agent instead of Claude. The facade is an ACP **v1** client (protocol version 1 only; the v2 draft is not negotiated). Facade-owned features are unchanged: thread records, list/read/pagination, queue, attachments, `fs/*`, `command/exec`, `process/*`, reconnect and approval replay. The provider id and name reported to Codex come from `--provider-id`/`--provider-name` (default: the executable name), and `modelProvider` must match it.

| Codex behavior | ACP mapping |
| --- | --- |
| Turn | `initialize`, then `session/new` (first turn), `session/resume`, or `session/load` (history replay suppressed), then `session/prompt`. As for Claude, a cleanly finished thread keeps its agent process for `--idle-session-timeout-seconds`, and the next turn with unchanged settings reuses it with another `session/prompt`. A turn that needs a new process resumes or loads the session; an agent with neither cannot continue a thread in a new process. |
| Instructions | ACP has no system prompt. Base/developer instructions, Codex plugin guidance and the desktop visualization directory are sent once, as a text block ahead of the first prompt of a new session. |
| Streaming | `agent_message_chunk` → `agentMessage` deltas (one item per message id); `agent_thought_chunk` → `reasoning` (hidden with `summary: none`). |
| Tools | `tool_call`/`tool_call_update`: `execute` → `commandExecution` (command from `rawInput`, output from content/`rawOutput`, streamed deltas, exit code); `edit`/`delete`/`move` → `fileChange` with unified diffs from ACP diff content; other kinds → `dynamicToolCall` under the provider namespace. The item type is fixed by the call's first kind. |
| Plans, notices | `plan` → `turn/plan/updated`; completed `compaction_update` → `contextCompaction`; `notice` → `warning`. Mode, command, config and session-info updates are ignored. |
| Approvals | `session/request_permission` → command, file-change or file-read approval by tool kind; other kinds use the generic once/session/deny question. Accept selects the agent's `allow_once` (else `allow_always`) option; decline selects `reject_once`; cancel answers `cancelled` and interrupts. Session grants and `approvalPolicy: never` behave as for Claude. An agent's `$/cancel_request` resolves the pending approval. |
| Interrupt | `session/cancel`; outstanding permission requests are answered `cancelled`. |
| Steering | `turn/steer` input is queued and sent as the next `session/prompt` in the same Codex turn, after the current prompt ends. |
| Models | `model/list` opens a probe session and lists the agent's `model` config option values (or the unstable `models` state). `default` keeps the agent's own selection. A selected model is applied with `session/set_config_option` (or `session/set_model`); an unknown model fails the turn. Effort maps onto a `thought_level` option value of the same name, else the agent default applies. Agents without image prompt support report text-only models and reject image input. |
| Usage | `usage_update` → context occupancy and window; prompt `usage` (unstable) → billing totals. |
| Desktop tools | Desktop dynamic tools and Codex plugin tools reach the agent as a stdio MCP server, `codex_desktop` (the facade's hidden `mcp-bridge` subcommand relaying to a private Unix socket). Calls run through the normal `item/tool/call` path; the agent's permission request for them is validated against the tool schema and answered by the facade. |
| Fork | Requires the agent's (unstable) `session/fork` capability, and only at the latest turn: `session/fork` copies the whole session, so the fork's first turn fails if the source thread has advanced since. |
| Ephemeral | The session is deleted with `session/delete` when the agent supports it. |
| Automatic review | `approvalsReviewer: auto_review` (or `guardian_subagent`) sends each permission request to a one-shot Claude reviewer instead of the user: `claude -p` with the Codex guardian policy (`protocol/codex-guardian`, vendored), a compact transcript (every user message plus recent activity), the exact action, read-only `Read`/`Grep`/`Glob` tools in the thread cwd, and a JSON verdict schema. Progress is reported with `item/autoApprovalReview/started`/`completed` (`decisionSource: agent`). Allow answers the agent's allow option; deny, reviewer failure, and timeout (`--auto-review-timeout-seconds`, default 90) answer reject (fail closed). As in Codex, three consecutive denials, or ten among recent reviews, interrupt the turn with a `guardianWarning`. `thread/approveGuardianDeniedAction` grants that exact action for the thread, records it for later reviews, and tells the agent (as steering input, or with the next turn). The reviewer is the `--claude` executable with `--auto-review-model` (default `sonnet`). |
